# cpubench (два бинаря: cpubench-ppc и cpubench-intel)

Синтетический бенчмарк CPU для Mac (Mac OS X 10.4/10.5). Измеряет два числа —
скалярную FP-пропускную способность и целочисленную ALU-пропускную способность.
Одна кодовая база, два артефакта, чистый C, один поток (решение 19.10.2026).

## Артефакты

| бинap            | платформа                      | тулчейн канонической сборки            |
|------------------|--------------------------------|----------------------------------------|
| `cpubench-ppc`   | G3/G4/G5, Tiger 10.4 + Leopard 10.5 | Tiger gcc 4.0.1 darwin8 — «младший» |
| `cpubench-intel` | i386, Leopard 10.5 (Core 2)    | gcc 4.0.1 darwin9, сборка на самой машине |

Вывод двух бинарей одинаковый по структуре строк: шапка (machine / cpu /
freq), фазы FP и INT с per-cycle строками, общий чексумма и total wall.
Осознанно различается одно слово внутри FP-блока: на PPC вторая строка
`FMADD/s` (там fused-инструкция существует), на Intel — `mul+add/s`
(FMA в этой эпохе не существует). Строка **GFLOP/s** идентична и
математически сравнима между архитектурами. Первая строка FP считает
**chain-steps** (проход всех цепочек), не отдельные операции.

## Метрики

| фаза | ядро | за пасс | отчёт |
|------|------|---------|-------|
| **FP** (ppc)   | 16 независимых цепочек `a = a*x + 0.5`; gcc 4.0.1 сворачивает в native `fmadd` (dbl 64-bit) | 16 FMADD = **32 флопа** | FMADD/s и **GFLOP/s** |
| **FP** (intel) | 8 независимых цепочек `a = a*x + 0.5`; компилятор даёт separate `mulsd`+`addsd` | 8 x (mul+add) = **16 флопов** | mul+add/s и **GFLOP/s** |
| **INT** (обе)  | 4 цепочки xorshift32 (только xor/shift, латентность 1 такт) | 8 раундов x 4 линии x 6 op = **192 ALU op** | **billion ALU ops/s** |

**Обе горячие петли register-clean** (дизасм-аудит обязателен, см. proof):
аккумулаторы/линии держатся локальными скалярами и снаружи цикла не
появляются; состояние гоняется load/store-set'ом РАЗ на вызов.
История: прежняя struct-индексированная PPC-версия измеряла LSU-bound
сценарий (16 ld/st на пасс; G4 удерживался на своём 1-LSU потолке
~0.5 flop/cycle) — исторические паспорта мерили именно её, прямое
сравнение со старыми числами некорректно, паспорта мерятся заново.
На i386 инт-версии per-round reload линий тоже съедал ~17% INT-рации.

## Метрики

| фаза | ядро | за пасс | отчёт |
|------|------|---------|-------|
| **FP** (ppc)   | 16 независимых цепочек `a = a*x + 0.5`; gcc 4.0.1 сворачивает в native `fmadd` (dbl 64-bit) | 16 FMADD = **32 флопа** | FMADD/s и **GFLOP/s** |
| **FP** (intel) | 8 независимых цепочек `a = a*x + 0.5`; компилятор даёт separate `mulsd`+`addsd` | 8 x (mul+add) = **16 флопов** | mul+add/s и **GFLOP/s** |
| **INT** (обе)  | 4 цепочки xorshift32 (только xor/shift, латентность 1 такт) | 8 раундов x 4 линии x 6 op = **192 ALU op** | **billion ALU ops/s** |

Почему цепочек не поровну: 32 FPR держат 16 аккумулторов целиком в регистрах
(PPC-стиль), а на i386 SSE2-32 всего 8 xmm — и ровно на 8 аккумулторов
финальное ядро уложено без пролова (см. proof). На Intel x выведен из горячей
петли (параметр вызова + рециклинг по счетчику пассов); на PPC x дрейфует
per-pass в окне [1.0, 2.0] шаг 0.01 (100-пассовое окно: рост цепочки
exp(sum ln x) ~ 5.8e16 — конечен, fold внутри unsigned long long).
На Intel x фиксирован на вызов (+0.0005 дрейф меж вызовами), рециклинг
каждые 16384 пассов (рост ~7e9 против прежних ~3e31 при 65536 — прежнее
окно давало UB-приведение в чексумму). Чексумма теперь честно определена
(fold внутри unsigned long long) — это proof-per-machine, не hash.

## Почему так (а не «рандомные операции»)

1. Ядра **детерминированные** с точным счётом операций — «случайность» не
   влияет на пропускную способность конвейера, зато ломает её учёт.
2. Фаза выполняется **чанками ~0.35 с**: часы читаются один раз за чанк и в
   конце фазы — overhead < 0.5 %, а метрика считается как «операции /
   фактическое wall-время», так что замер самокорректный.
3. **Прогрев перед каждой фазой** (неучитываемый чанк): 970FX/G4 просыпаются
   из простоя на пониженном P-state и разгоняются по ходу; без прогрева
   замер занижает до 40 %.
4. Итоговый чексумма печатается в конце — **proof of real work**: работа
   не выброшена оптимизатором, машина считала честно.
   Чексуммы PPC и Intel **не сверяются меж собой** (fmadd — одно округление
   на шаг, mul+add — два: значения битов diverge, это норма); чексумма —
   proof-per-machine, не кросс-арх сравнение.

## Запуск

```
./cpubench-ppc          # FP 10 с + INT 10 с (~21 с с калибровкой и прогревами)
./cpubench-ppc -t 3     # быстрый дымой-прогон

./cpubench-intel        # то же самое на Intel-машине
```

Каждая фаза печатает: опись переданного workload'а, фактическое wall-время,
rate в млрд ops/s, **per-cycle строку** (flop/cycle и alu-op/cycle — тактовая
частота уже в шапке; leopard-кварк HW_CPU_FREQ `<<32` обработан).
В конце — общий чексумма и суммарное wall.

## Сборка

Единые флаги репозитория `gcc -std=gnu99 -O2 -Wall` — 0 warnings на обеих
архитектурах. тоже — make подбирает имя цели по `uname -m`; для PPC добавлен
`-force_cpusubtype_ALL` (G3-совместный подтип ppc/ALL). Каждый артефакт
собирается на своей машине, и оттуда же бинарь сливается в repo:

```sh
# PPC (канон — Tiger, gcc 4.0.1 darwin8):
ssh ibook-g4-1ghz ; cd ~/Projects/cpubench ; make clean && make

# Intel (по протоколу внедрения — сборка локальная, с неё же сливаутся бинари):
ssh intel-leopard ; cd ~/Projects/cpubench ; make clean && make
```

## Доказательства честности ядер (протоколы 20.10.2026)

1. **Geometry sweep** (`/tmp`-пробник на intel-leopard): классическая 8-цепочечная
   форма дала **2.67 GFLOP/s** — выше mul/add-лент (1.7–2.0 GFLOP/s) и
   16-цепочечной классики (2.35 GFLOP/s с проловами: 16 не влезают в 8 xmm).
   Выбор по факту плато, а не по вкусам.
2. **Disasm-audit финальных бинарей** (`otool -tv/-tV`, тела `_fp_run`/`_int_run`):
   - PPC: петля = 3 const-загрузки + **16 fmadd + fadd** + cmp; **0 lfd/stfd
     аккумулаторов** (все 16 в FPR, r-микс r2..f31); INT: линии r26..r30
     через все пассы, `bdnz` на раунд;
   - Intel FP: 24 mul/add, из них на память только константы literal pool,
     аккумы — xmm; INT: 2–3 линии в GPR, четвёртая на стеке — известный
     регстрейн i386-gcc 4.0.1 (толкает НЕ asm-магию, документировано).
3. Physics-границы честные: рост цепочек конечен и внутри ULL (см. таблицу
   метрик; прежние окна на обеих арках давали inf/UB-cast в чексумму).
4. INT-ядро на обеих архитектурах поровну по тексту (xorshift32, 4 линии) —
   прямая сравнимость числа.
5. **Валидация методологии 20.10.2026 (второй прогон уже после-фиксы,
   по 2 полных прогона, разбежка ≤0.5%):**
   - ibook-g4 (7447a, 1.0667 GHz): FP **1.121 GFLOP/s = 1.051 flop/cycle**,
     INT **2.37 млрд ALU ops/s = 2.22 op/cycle**;
   - intel (Core 2 T7700, 2.4 GHz): FP **2.655 GFLOP/s = 1.106 flop/cycle**,
     INT **3.43 млрд = 1.43 op/cycle**;
   - per-cycle теперь честный между арками в одной шкале (scalar-double
     both): Core 2 ≈ G4 в FP-флопах на такт (1.11 vs 1.05), INT-план —
     G4 солидно вперед (2.22 vs 1.43, xor-shift только на ALU).
   - **Паспорта прошлых прогонов (G5 и прочие) = LSU-bound вариант ядра,
     с новыми числами напрямую не сверяются** — мерить все машины заново.

## Дизайн-решения

**Multi-core режим НЕ делаем** (19.10.2026). Суть проекта — сравнимость
**одноядерной** производительности: замеры по одной ячейке позволяют
сравнивать G3/G4/G5/Intel по такту. Считать ядра машины — не наша задача;
нагрев обоих ядер, если потребуется, делает cpuburn. Если когда-нибудь
решение пересмотрят: sketch — `-j N`, pthread, XOR-объединение чексумм.

**Intel-ветка** (20.10.2026): отдельный артефакт из одного исходника,
per-arch ядра не скрывают разницу FMA/не-FMA — она видна в самой сводке
(сравнение через GFLOP/s, метки различаются).
