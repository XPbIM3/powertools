# Intel-стек Mac: телеметрия и батарея (живая записка)

Цель записки — быть готовыми к появлению Intel-маков в парке (пока это
MacBook Pro 3,1, но по мере онлайна других машин дополняем). Здесь
сведено всё: что публично в IOKit-реестре, что за SMC user-client'ом,
и — самое ценное — **расшифрованный каркас SMC-протокола**, который
снимает с нас необходимость повторного Reverse Engineering'а.

Решение проекта: Intel-стек — исследовательское направление, код проектов
не трогается, пока телеметрия SMC не будет устойчиво выбрана; no fan control
(фиксированные обороты/запись ключей) — никогда.

## 2. Что публично в реестре (без user-client — уже весь максимум)

Корень графа — **AppleACPIPlatformExpert** (ACPI-иерархия, не device-tree):
узлов device_type=battery/PMU нет вообще.

### Термостек

`ACPI_SMC_PlatformPlugin` (IOPlatformPlugin) публикует словари — те же
**`IOHWSensors` / `IOHWControls`**, что fanmon читает SMU-путём на G5:

- `IOHWSensors` — **один сенсор**: `location="GPU"`, `type="gpu"`
  (не `"temp"` — фильтр TEMPERATURES fanmon'а его пропустит).
  Live-значение ~6553600 → 16.16 ≈ **98-100 °C** под компил-нагрузкой
  (между снимками плавает на ~2° — данные живые). Для 8600M GT правдоподобно,
  но калибровка масштаба 16.16 для type="gpu" — открытая проверка.
  На сервисном узле `IOHWSensor` (AppleHWSensor,
  `IOPropertyMatch device_type=gpu-sensor`) live `current-value` — второй
  источник того же сенсора.
- `IOHWControls` — **5 лимитных контролей** (AppleSMCControl, `type="smc"`):
  cpu/gpu/mem plimit + cpu/gpu state. Это throttle-лимиты, **не вентиляторы** —
  `fan-rpm`-контролей в графе нет.
- Плюс `IOHWCtrlLoops` (PID-мета-циклы Normal/Reduced Power/...) и
  `IOEnvironment` (external-overtemp, chassis-switch, control-failed).
- ACPI **ThermalZone-узлов ноль** (grep проверен) — Apple всё спрятала в SMC.
- `AppleACPIACAdapter` — объект присутствия AC (ACPI0003) без показаний;
  `boot-ec` — голый узел; `LID0` — крышка; `AppleLMUController` — ambient light,
  не термометрия.

**Вентиляторы и «настоящие» температуры (die/heatsink/palm-rest) в реестре
НЕ публикуются вообще** — только через `AppleSMC` (см. §3).

### Батарея (AppleSmartBattery) — публично почти всё

- Capacity/MaxCapacity/DesignCapacity = 2377/2377/5200 мА·ч — **обычные
  мА·ч, без ×10** (сравнение с pb15, где 54059, показывает: единицы
  ×10 — не постоянная Leopard'а, а особенность конкретной машины/стека —
  при переносе batinfo всегда сверять масштаб по DesignCapacity!).
- **`CellVoltage` = (3909, 4133, 4132, 0)** — по-ячеечные напряжения,
  сумма 12174 = Voltage. 3S-пак + пустой слот. На G3/G4 недоступно публично.
- `BatterySerialNumber` = "SMP-ASMB012-3eeb-5ee", `CycleCount` = 38.
- `Temperature` = 3002 → 30.02 °C (в единицах 1/100 °C).
- `LegacyBatteryInfo` — PMU-формат словаря (Capacity/Voltage/Flags/Cycle Count).
- Health = 2377/5200 = 45.7 % — изношенный образец, хороший тест-кейс
  для health-логики batinfo.

**Резюме по категориям (публичный реестр):**
температуры — GPU + батарея; напряжения — батарейный pack+cells;
токи — `Amperage`/`InstantAmperage` (на AC ноль); обороты — ничего.

## 3. SMC user-client: расшифрованный каркас (РЭ по символам kext 10.5.8)

Ключевое достижение экспедиции 10.0.1.25: протокол прочтён с бинаря
`/System/Library/Extensions/AppleSMC.kext/Contents/MacOS/AppleSMC`
(**символы оставлены Apple** — `nm`/`otool`/gdb всё показывают), плюс
двухтактная эмпирика пробниками. Расшифровано ~80%; путь чтения значений —
остаток (см. §5).

### Механика

```c
service = IOServiceGetMatchingService(kIOMasterPortDefault,
                                      IOServiceMatching("AppleSMC"));
IOServiceOpen(service, mach_task_self(), 0, &conn);   // type 0
kern_return_t kr = IOConnectCallStructMethod(conn, 2,   // selector 2
                                             &in, 80,   // вход ровно 80 байт
                                             &out, &sz);// выход ровно 80 байт
```

- Selector таблицы kext'а (`getTargetAndMethodForIndex`): существенные
  методы — 0,1 (скалярные, не наш интерес), **2 = smcYPCEventCheck**
  (структура 0x50=80 байт, verified по sMethods: sizes 0x50/0x50).
- SMC-команды (внутри) — это же коды прошивки: **jump-таблица
  `smcHandleYPCEvent` по `(байт@+0x2A) - 5`**, 8 исходов.

### Раскладка 80-байтовой структуры (byte offsets, эмпирика + дизасм)

| offset | поле | примечание |
|---|---|---|
| +0x00 | key dword | **байты ключа в перевёрнутом порядке** (см. ниже) |
| +0x04 | SMCVersion (8) | нами не заполнялось, zeroes ok |
| +0x0C..0x1B | ??? | не исследовано (живые нули работали) |
| +0x1C | dword: **expected size при чтении** | cmd 6 читает отсюда (гипотеза, см. §5) |
| +0x28 | **байт-статус ОТВЕТА** | 0 = ok; 2 = «нужен root»; 0x84/0x86/0x89 = ошибка операции |
| +0x2A | **байт КОМАНДЫ** | 5..12 |
| +0x2C | dword: index (cmd 8) / результат cmd 7 | |
| +0x30..0x4F | **32 байта данных** | read/write payload; на выхлопе ответ лежит здесь |

keyInfo на выхлопе (после cmd 9): **+0x1C dataSize байт, +0x20..0x23 dword
dataType, +0x24 dataAttributes** — приятная симметрия: размер читается
оттуда же, откуда cmd 6 берёт expected size.

### Команды (байт @+0x2A)

| cmd | действие | слот vtable → функция |
|---|---|---|
| 5 | **WRITE** байтов | smcWriteKeyWithSMC(key,size,buf) |
| 6 | **READ** байтов — **только root** | smcReadKeyWithSMC(key,size,buf) |
| 7 | кол-во ключей | smcGetKeyCount(m*) |
| 8 | ключ по индексу | smcGetKeyFromIndex(m, m*) |
| 9 | получить keyInfo ключа | smcGetKeyInfo(m, SMCKeyInfoData*) |
| 10/11 | notification-механика | smcRegister/UnregisterNotificationController |
| 12 | — | register-контроллер |

### Root-гейт (расшифрован чётко)

`AppleSMCClient::initWithTask` сохраняет
`clientHasPrivilege(task, "root")` в поле клиента **+0x80**;
`smcYPCEventCheck` ругается (e00002c1 + out+0x28 = 2, kprintf
«not authenticated as root») **только на команду 6 у не-root'а**.
Команды 5 (!), 7, 8, 9 работают и не-root'у. Мы всегда работаем через
`sudo` — просто чтобы не ждать сюрпризов. **Запись ключей (cmd 5) нами
не используется никогда** — только чтение.

### Форматы ключа — главная ловушка

Байты ключа в структуре **перевёрнуты относительно ASCII-строки**:
строке `#KEY` соответствуют байты `YEK#` (наш принятый порядок «B»).
Проверено эмпирикой: порядок A («#KEY» как есть) → статус 0x84 на cmd 9;
порядок B → **статус 0, keyInfo возвратился: dataSize=4,
dataType=0x0482FD14 (LE-дочитанный dword; семантика уточняется при дожиме),
dataAttributes=0x80**. При выводе печатаем строку ключа обратно
разворотом байтов.

### Перечисление ключей

cmd 8: индекс — dword в входном +0x2C; результат — key dword на выходе.
Индекс 0 на MBP3,1 = сам `#KEY`. **Работает.**

### Чего НЕ работает пока (и это остаток работы)

- **cmd 7 (кол-во ключей)**: результат на out+0x2C пришёл мусорный
  (0xF500_xxxx). Вероятно, kext ждёт внутренний указатель или надо
  заполнить ещё что-то — при дожиме выправить.
- **cmd 6 (чтение значений)**: статусы 132 (0x84) / 134 (0x86) — данные
  на +0x30 нули. Кандидаты на причину: (а) dword размера не там/не в том
  формате (+0x1C — наша гипотеза из дизасма), (б) чтение кэшируется и
  надо сначала cmd 9, (в) особенности YPC-диспетчера. Это **30-60 минут
  эмпирики** — каркас уже известен.

## 4. Ожидаемые ключи MBP3,1 (community-канон; верифицировать при дожим)

- Вентиляторы: `F0Ac`/`F1Ac` — RPM (формат `fpe2`: fpe2/4),
  `F0Mn`/`F0Mx`, `F1Mn`/`F1Mx` — min/max, `F0Sf`/`F1Sf` — safe.
- Температуры: `TC0D` (CPU die), `TC0P` (proximity), `TH0P`, `TM0P` и пр.
  (`sp78` → value/256 °C).
- Power: `PA0P`-типа ключи — может и нет на 2007-м; снимем дампом.
- Полный список заранее неизвестен — поэтому план: перечисление (cmd 8)
  и полный дамп keyInfo.

## 5. План дожима (когда машина снова онлайн; 30-60 минут)

1. Перенести пробник (`scp -O`). Основа — C-каркас из §3: вся механика
   (smc80-вызов, раскладка, порядок байтов ключа) описана здесь целиком,
   переписать ~80 строк.
2. Верифицировать cmd 7 (count) — сначала «пустой» вызов, посмотреть
   out+0x2C; если мусор — попробовать заполнение key = `#KEY`.
3. Цикл: cmd 8 (перечень) → cmd 9 (keyInfo: size+type) → cmd 6 (данные).
   Если cmd 6 упорно даёт 0x84/0x86 — выправить поле размера
   (+0x1C dword vs байт) и/или порядка вызовов (9→6).
4. Полный дамп ключей (ожидаем ~100-400 шт.) в CSV: key,type,size,attr,
   bytes,decoded. Классификация: F-фан, T-темп, P-мощность; единицы —
   по формату (sp78→/256, fpe2→/4, flts — 4 байта float).
5. Валидация на живость: дать нагрузку → RPM/°C должны шевелиться;
   сравнить с показаниями GPU-сенсора (§2) и батареи.
6. Отчёт: дописать в этот файл (машина, найденные ключи, единицы).
   Тогда вопрос «fanmon-Intel» — станет вопросом 150 строк кода.

## 6. Границы и принципы

- SMC user-client — **категория «полуприватный user-client»** (как
  ApplePMUUserClient на PPC). Решение проекта: для парка G3/G4/G5 это
  не нужно (там PMU/SMU, SMC-чипов нет); для Intel-машин — поддержка
  «по мере онлайна», в режиме read-only, по явному поручению.
- Расшифровка комплектом symbols/otool/gdb + эмпирика — **однократна**;
  записан в этом документе. Не повторять дизасм-погружение без причины:
  каркас уже известен.
- Не ломать: никаких записей в SMC (cmd 5), никаких перезапусков
  драйвера, никаких кекстов.
- Пробники живут только в `/tmp` удалённой машины, удаляются после.

## 7. Хронология

- **Первый визит** (реестр, без SMC): термостек ACPI_SMC_PlatformPlugin,
  батарея, лимитные контроли. Задача: «посмотри, что даёт Intel-мак».
  Коммит `56a3275`.
- **SMC-экспедиция** (01-разведка): selector 2, 80-байт структура, команды
  5-12, root-гейт, порядок байтов ключа, cmd 9 + cmd 8 работают; cmd 6/7 —
  остались; пробники удалены. Коммит `3303eae`.
- **Документ-консолидация** (этот файл): слито всё в одну записку
  `notes-intel.md`, старый `notes-intel-mb31.md` удалён (полностью впитан).
