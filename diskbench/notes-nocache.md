# diskbench: исследование — честность F_NOCACHE и асимметрия write < read

Дата: 19.10.2026 · Машина: powermac-g5 (PowerMac7,3, Leopard 10.5.8) · Пробник: временный C-файл
в /tmp, удалён после визита (по протоколу).

## Конфигурация диска (важно для трактовки всех цифр)

**RAID 0 из 2×250 ГБ** (оба ST3250410AS — Seagate Barracuda 7200.11), страйп
**128 КБ**, объём тома ~460 ГБ свободных. Это значит:
- скорость >100 MB/s на linear здесь **реальна для конфигурации**, а не утечка
  кеша — две очереди голов параллелят стримы;
- в заметках парка линейные цифры iMac G5 (SATA-1, одиночный диск, 20–43 MB/s)
  — несравнимы с этой машиной напрямую;
- random 4K страйп не помогает (блоки 4K всегда попадают в один член массива).

## Вопрос

Наблюдение: linear read (120–139 MB/s) стабильно быстрее linear write (~99 MB/s),
хотя «на HDD запись обычно быстрее чтения». Нет ли скрытого кеширования при чтении,
несмотря на F_NOCACHE?

## Эксперименты

| # | Опыт | Результат | Вывод |
|---|------|-----------|-------|
| E1 | 512М чанк, 3 чтения подряд (F_NOCACHE + F_RDAHEAD off) | 139 → 130 → 131 MB/s, платр-стабильно | **OS-кеша нет** — pass2/3 не быстрее pass1 (кеш бы дал сотни MB/s из RAM) |
| E2 | cold-read живого системного файла (/var/vm/swapfile0, sudo) | **1146.8 MB/s** (!) | caveat: swapfile — VM-mapped vnode, живёт в UBC; **F_NOCACHE не гарантирует bypass для спец-вндов**, только для обычных файлов |
| E3 | write 512М (F_NOCACHE, без флаша) + отдельно F_FULLFSYNC | write 99.2 MB/s; **флаш 0.058 с** | флаш привода нипричём: write и без него ~99 |
| E4 | тот же write, блок 16М вместо 4М | те же **99.2 MB/s** | границы блоков/журнал HFS+ нипричём: write — устойчивый плато |

Привод: **2×ST3250410AS в RAID 0** (Seagate Barracuda 7200.11, 250 ГБ каждый,
страйп 128 КБ) — поздняя замена; паренные диски, скорость >100 MB/s — реальная
для этого массива (не кеш). В iMac G5 времён парка стояли SATA-1 одиночные
~20-43 MB/s — сравнение несравнимо.

## Выводы

1. **Кеш-утечки нет**: F_NOCACHE для обычных файлов работает честно; числа чтения
   стабильно платривые от прогона к прогону (и это на RAID 0, где скорость >100
   MB/s — реальная, заряду достижима обе головами).
2. **«Запись быстрее чтения» — только интуиция buffered-бенчей** (там write мгновенно
   уходит в кеш привода/ОС, read ждёт пластинки). В честном nocache-режиме
   sustained write ≈ 10–25% ниже sustained read — физика (запись на пластину
   дороже чтения) + RAID-оверхед, а не механизм кеша.
3. Финальный F_FULLFSYNC в нашей write-фазе почти ничего не стоит (~0.06 с
   на 512М стрим) — разносить счёт не «заваливает» write-цифру.
4. Уникальный кейс: для спец-вндов (swapfile, mapped) F_NOCACHE не спасает —
   1146 MB/s из RAM. Если когда-нибудь измеряешь системные файлы — не верь
   «nocache» на mapped vnodes.
5. При опознании привода был ошибочный вывод «одиночный ST3250410AS» —
   в ioreg-выводе модель фигурировала **двумя строками** (диск 0 и диск 1) —
   RAID-пара. Урок: «дубли» в ioreg могут быть парой реальных устройств.

## Open вопрос

Разброс read-цифр между прогонами (112–139 MB/s) — зоны диска (крайняя/середина
пластины) в зависимости от того, куда легли extents. Для точных паспортов
полезно фиксированное место чанка (-p) и/или несколько прогонов.
