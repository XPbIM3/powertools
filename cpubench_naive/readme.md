# cpubench_naive

Грубые («dirty») метрики производительности CPU на максимально тупом коде,
собранном с **нулевыми оптимизациями** (`-O0`). Одно ядро-исходник, одинаковые
правила на всём парке G3/G4/G5/Intel.

Философия: бинарь меряет **не пик FPU/ALU**, а «что делает наивный C».
На `-O0` каждый локал живёт на стеке, каждая операция — load-op-store плюс
адресная арифметика, без разворачивания, без выравниваний, без специкодов.
Единственная допустимая арч-разница — то, что *печатается*, а не то, что
*считается*.

## Ядра

Оба ядра: 8 лейнов, мешалка «сам + сосед», ровно **1 add + 1 mul на лейн-пасс**
= 16 ops/пасс в ОБЕИХ фазах (гомогенный op-микс):

```
FP : a[k] = (a[k] + a[(k+1) & 7]) * x[k]        x[k] = 0.5 + (k+1)·1e-9
INT: u[k] = u[k] * 1664526u + u[(k+1) & 7]      (32-бит, wrap легален)
```

- **FP:** среднее с соседним лейном имеет спектральный радиус ровно 1
  (значения ограничены); лёгкий перекос x чуть раздувает общий масштаб,
  но горизонта переполнения (~1e10 пассов) в любом замерном окне не
  достигнуть. Нулей и денормалов нет по построению (все лейны положительные).
- **INT:** det матрицы перехода = c⁸−1, при чётной константе он нечётен →
  матрица **обратима mod 2³²** → орбита, стартовавшая из ненулевого
  состояния, не может ни «прибиться» к фиксированной точке (чем страдала
  наивная версия `u ← 2u+1`: джем на 0xFFFFFFFF после 32 пассов), ни
  выродиться вообще.
- Семантика счёта: **1 op = один mul или один add** (учёт load-op-store
  и цикл входят в цену, это и есть «грязный» замер).

## Режимы

```
naive                 # FP 10 с + INT 10 с, считаем «сколько наделал»
naive -t SECONDS      # длина каждой фазы
naive -n PASSES       # фиксированное число пассов на фазу (детерминизм)
```

- `-t` — режим метрики: все машины работают одинаковое время, сравниваем
  GFLOP/s и Gop/s. Число пассов (и чексуммы) между машинами заведомо разные.
- `-n` — режим proof-of-rules: одинаковый проход на всех машинах →
  **чексуммы обязаны совпасть на G3/G4/G5/Intel**. Совпали — правила
  (округления, последовательность, объём работы) везде одни и те же;
  разошлись — где-то вкралась арч-разница (кандидаты: x87 80-бит
  промежуточные на i386, FMADD-фьюжн на PPC, которые надо ловить
  otool-аудитом и volatile-сплитом).

## Тайминг

Часы (`gettimeofday`) проверяются раз в **1024 пасса**, не каждый пасс:
syscall ~1 мкс, а пасс на `-O0` — сопоставимая цена, пер-пассная проверка
меряла бы syscall. Overshoot чанка < 0.1%.

## Выход

```
machine: PowerBook5,6
cpu:     G4 (7450 family, subtype 11)  (на Intel: brand string)
freq:    1670 MHz
naive -O0: FP 10s + INT 10s, 8 lanes, 16 ops/pass, chunk 1024

  FP :   0.000 GFLOP/s    10.00 s   ...  passes   0.000 op/cycle
  INT:   0.000 Gop/s      10.00 s   ...  passes   0.000 op/cycle
  checksum: fp ........  int ........
```

ops/cycle — главный индекс для парка 500 МГц–2.5 ГГц (частота из
`hw.cpufrequency`, эвристика «Leopard иногда отдаёт Hz<<32» в коде есть).
`0.000 op/cycle` = частоту sysctl не отдал.

## НЕ путать с оптимизированными замерами

Цифры `-O0`-наивности нельзя подмешивать к каким-либо «пиковым»
колонкам (FMADD/xorshift-класс): это разные миры. В
`cpu_bench_baseline.md` для naive — свои колонки/раздел.

## Сборка

Два слоя G3-safe (`-mcpu=G3` + `-Wl,-force_cpusubtype_ALL`),
все артефакты собирать на canonical-машине (ibook-g4-1ghz, Tiger/gcc-4.0.1).
После сборки — верификация по скиллу ppc-build: `otool -hv` (подтип
`ppc/ALL`), отсутствие AltiVec-мнемоник в `otool -tv`, плюс для FP-секции —
отсутствие `fmadd` (иначе разнос умножения/сложения через volatile-темп).
`md5` бинаря после доставки в репо должен совпасть.
